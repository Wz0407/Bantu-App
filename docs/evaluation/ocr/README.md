# OCR evaluation (Phase 2, Gate B)

Engine: **tesseract.js 7** (Apache 2.0, WASM, fully in-process) with
**tessdata_fast** language data (Apache 2.0) for `eng`, `msa`, `chi_sim`,
installed locally by `scripts/model-setup/setup-ocr-data.py`. No cloud OCR; after
setup the OCR path makes no network requests.

Fixtures: synthetic notices under `data/samples/images/` generated by
`generate_fixtures.py` (clean en/ms/zh + one degraded en with rotation, blur and
noise). All content is invented.

## Measured results (this machine — see `ocr-eval-results.json`)

| Fixture            | Literals preserved | Confidence | Time   |
| ------------------ | ------------------ | ---------- | ------ |
| notice-en.png      | 3/3                | 95%        | 365 ms |
| notice-ms.png      | 3/3                | 95%        | 407 ms |
| notice-zh.png      | 2/3                | 93%        | 469 ms |
| notice-en-degraded | 3/3                | 78%        | 393 ms |

## Known limitations (recorded honestly)

- **Chinese amounts embedded in CJK text**: `RM88.00` inside the zh fixture was
  not recognized cleanly by `chi_sim` alone (Latin/digit segments inside CJK
  lines are a known Tesseract weak spot). Amount-bearing Chinese documents are
  better served by the text-PDF/TXT path; the UI surfaces OCR confidence and a
  low-confidence warning so users check extracted numbers against the original.
- **Scanned PDFs are not OCRed** (deferred finding D5): pages without a text
  layer produce an explicit warning instead of silent empty output.
- Rotation beyond a few degrees or heavy noise degrades accuracy; the degraded
  fixture (1.5° + blur + noise) still passed but with confidence dropping to 78%.
- Multi-language `auto` OCR loads all three language packs and is slower; a
  language hint from the upload form gives the best results.
